# Pull robot CAD once, use the team library everywhere

One teammate opens the robot's saved version in Onshape intake, chooses **Find robot parts**, then **Sync robot to team library**. All available unique part types in that source/configuration are pulled in batches, including purchased geometry for the catalog. Every successful CAD pull automatically saves an immutable snapshot to a durable local upload queue and sends it to Foundry cloud. There is no separate project export, sharing action or teammate Onshape import. A saved robot URL alone does not contain geometry. Unavailable/suppressed parts are not fabricated as cached solids. Initial pulls consume the protected Onshape allowance; the app does not crawl every document or silently follow a changing workspace.

Foundry's start page automatically lists **all team parts** after GitHub sign-in, without a teammate Onshape connection. Search across stored snapshots by robot, part, material or subsystem; optionally narrow to an exact snapshot. Choose parts from one work order and add them to draft plates. The native service downloads and checks geometry in the background, one snapshot at a time, and saves it under per-user application data. It refreshes the cloud catalog at startup, when Team parts opens, when the network returns and every five minutes. The website refreshes its catalog once per minute and offers portable projects for selected parts. Old portable-project sharing remains under Advanced.

**Offline use:** snapshots marked Saved on this laptop can be opened and prepared after disconnecting or restarting. Browser origin/ephemeral local ports do not own this cache; it is persisted by the local service. Uploads interrupted by a cloud outage remain queued and retry from local bytes, without another Onshape request. Cloud capacity failures remain visible, with pending data retained. A fresh laptop needs one online download first. The static website itself is not an offline-installed application. Shared manufacturing reservations still require the live service; cached geometry does not authorize duplicate offline print starts.

Normal library listing, cloud downloads, upload retries, offline preparation and reprints use zero Onshape calls. They use Foundry's authenticated Cloudflare Worker/D1 storage and the local cache. GitHub Pages hosts static UI only. This is the existing cloud store, not a newly provisioned R2 bucket or unlimited storage. Explicitly pulling a new CAD version is the only route to newer geometry; existing snapshots/jobs are never silently replaced.

Snapshots preserve original geometry/units/hashes, immutable CAD IDs/configurations, installed occurrence transforms, CAD quantities and subsystem memberships. Downloads independently check the compressed archive hash, expanded content hash, published metadata, mesh bounds and original-byte integrity before accepting parts. The portable project retains the same source-copy identity for existing work-order duplicate-manufacturing reservations.

Sharing does not copy jobs, approvals, toolpaths, machine/material qualification, physical checks, part-status claims or private part notes. Backup quantities start at zero and are chosen explicitly per job. Purchased/unavailable parts are excluded from print selection. Fixture sources retain their fixture identity and remain non-manufacturable. Profiles, placement/fit, use case and approvals still require review.

The workspace currently allows any signed-in GitHub account at the owner's request. The Onshape pull screen states that its automatic cloud copies are available to that audience even without Onshape document access. Anonymous/expired/removed cloud sessions are rejected; CAD credentials are never included. Local caches and pending uploads are scoped to the encrypted account session and service, and become inaccessible through the app after explicit sign-out or an account/service change. Previously downloaded local projects remain on their recipients' devices. The uploader can remove a cloud snapshot; the next successful catalog refresh drops it from the current local library. There is no claim that offline files can be remotely revoked.

Storage is bounded to 20 snapshots per team, each at most 24 MiB of expanded CAD JSON and 6 MiB gzip (with at most 512 KiB of catalog metadata). Oversized robots must be shared by subsystem rather than silently truncated. Compressed data is chunked into rows below D1's row limit, committed atomically with the catalog, and never read before authentication. Repeated identical uploads reuse the immutable ID; full-library failures leave no partial snapshot. There is no silent storage eviction or API-budget reset.

No private robot geometry is uploaded by development checks. Live acceptance uses a clearly labeled non-manufacturable fixture, removes that exact test snapshot afterward, and compares the protective Onshape counter before/after. User robot snapshots appear only after their uploader's sharing action.
